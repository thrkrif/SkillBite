## 1. 우리 기준 요약

- `docs/SKILL_SPEC.md`: 입력은 `/스킬이름 [내용]` 한 줄이면 동작. 말투·길이·금지어는 파일 상단 한곳에 모음. 사용자가 말하지 않은 사실·수치·사례는 쓰지 않고 `[확인 필요]`. 내부 정보·개인정보가 보이면 먼저 확인. 파일 저장 가능 여부는 단정하지 않음. `.hwp`는 만들지 않는다고 알림.
- 기존 5개 스킬은 모두 1.0~1.9KB의 짧은 합니다체 지시문이다. 구조는 "고칠 수 있는 설정 / 하는 일 / 지키는 것"이고, 첫 단계에서 한 번에 모아 묻는다(예: `doc-writer-word`).
- 한계: 한국 업무 문서 관행(개조식, 항목 기호, 공문 날짜 표기)이 거의 없다. 입력이 비었을 때의 행동, 출력 틀(표·기호)이 없다. 이 부분은 후보 중 stanlee7 쪽이 확실히 낫다.

## 2. modu-ai/moai-cowork

공통 관찰:
- 한다체(~한다) 지시문이다. 사용자에게 보이지 않는 지시문이므로 큰 문제는 아니다. 다만 우리 파일은 합니다체라 맞추는 작업이 든다.
- `metadata.version`, 다른 스킬 참조(`moai-writer:...`, `moai-coworker:...`), 외부 MCP(`kordoc`, WordPress.com MCP) 전제가 본문에 섞여 있다. SKILL.md 하나로 내려받는 사용자에게는 깨진 링크가 된다.
- 문서 대부분이 "~를 확인한다" 식 점검 문장이다. 첫 질문, 기본값, 출력 틀이 약하다.

### 2-1. content-blog (2점, 참고만)
- 분량: SKILL.md 3.5KB + references 6개(약 7.4KB). 읽은 파일은 SKILL.md, `naver-blog.md`, `tistory.md`, `seo-geo.md`, `wordpress.md` 앞부분이다. `brunch.md`, `ghost.md`는 미확인.

- 출력 형식: "결과에는 제목, 본문, 확인한 출처, 미확인 사실을 적는다" 정도다. 글 틀(소제목 구성, 길이)이 없다.
- 개발자 전제: SEO·GEO, Search Console, robots.txt, 스키마 같은 용어가 나온다(`seo-geo.md`). WordPress MCP 발행 단락도 있다.
- 이상한 부분: 결과와 발행 단락에 "ChatGPT Images 2.5", "Flare·Sunburst API 모델 ID", "Higgsfield", `moai-media:media-codex-image`가 나온다. 일반 사용자의 Claude 환경에서는 없는 것을 전제로 한 문장이라 그대로 두면 오작동 소지가 있다.
- `naver-blog.md`(1.3KB)는 글쓰기 기준이라기보다 "순위를 보장하지 않는다"는 주의문이다. 네이버 에디터 입력 같은 실제 도움이 없다.
- 우리 `blog-writer-naver`와 비교:
  - 더 나은 점: 규칙이 충실하다. "경험담·후기·사용 사례는 실제 작성자 자료가 있을 때만 쓴다", "통계·제품 효과·가격·일정·인용은 원출처와 기준일을 확인한다", "검색 상위 노출·AI 인용·전환율을 약속하지 않는다".
  - 부족한 점: 브라우저 게시 보조, 확인 지점, 설정 블록, 기본값, 입력 부족 시 행동이 없다.
- 판정: 우리 것을 유지한다. 위 세 규칙을 `blog-writer-naver`/`blog-writer-tistory`의 "지키는 것"에 한 줄씩 옮기는 것만 권한다. 후기·경험담 지어내기 금지는 SPEC의 "지어내지 않기"와 같은 방향이지만 블로그 후기에 특히 필요하다.
- 번역 난이도: 이미 한국어다. 다만 쓸 수 있는 내용이 적어 합치는 효용이 낮다.

  - 부족하거나 위험한 점: 계약서·공문 작성을 부추기는 문구("계약서 DOCX로 작성해줘")가 있는데 법적 검토 안내가 없다. 입력이 부족할 때 무엇을 묻는지 정해져 있지 않다("내용 수집 및 구조화"만 있다).
- 판정: 우리 것 유지. 문서 유형별 구조 목록을 `doc-writer-word`의 설정 예시에 반영하는 정도만 참고한다.

## 3. stanlee7/korean-office-skills

저장소 구조: 스킬마다 `SKILL.md` + `예시/` 폴더 2개 파일. 스크립트 없음. SKILL.md는 2.4~4.2KB로 짧다. 전체 8개를 읽었다. `예시/`는 `report-gaejosik`만 읽었고 나머지는 미확인. README는 앞부분만 읽었다.

공통 장점(우리 기준에 가장 가깝다):
- 구조가 "지킬 규칙 / 기본 형식 / 예시"이고, 출력 틀(표, 기호)이 코드블록으로 고정되어 있다. 출력 형식이 명확하다.
- 지어내기 금지가 구체적이다. "숫자는 원문에 있는 것만 씁니다", "메모에 없는 성과, 다음 주 계획, 이슈를 지어내지 않습니다".
- 회사 양식 우선 규칙이 있다. "회사 양식이 먼저입니다. 사용자가 양식(...)을 주면 ... 아래 기본 형식은 쓰지 않습니다". 한국 직장 현실에 맞다.
- 모호한 값의 처리가 정해져 있다(`미정`, `작성 필요`, `확인 필요`). 마지막 줄에 "작성 필요 칸 목록"을 모아 준다.
- 쉬운 말. 합니다체 + 개조식(~함, ~임)을 구분해 쓴다.
- 개발자 전제 없음. 스킬 본문에 터미널·git·설치가 없다(설치 안내는 README에만 있고 우리는 쓰지 않는다).

공통으로 고칠 곳:
1. 본문이 `예시/입력_메모.md`, `예시/기대출력.md`를 가리킨다. SKILL.md 하나로 배포하므로 파일 참조를 지우고 짧은 예시 1개를 본문에 넣는다(`report-gaejosik`의 예시는 이미 짧다). 인라인 예시는 가상 데이터라고 명시되어 있다.
2. frontmatter의 `license: MIT`, `metadata`(category, locale)는 우리 형식(`name`, `description`)에 없다. 출처·라이선스 표기는 라이선스 검토자 판단에 따라 별도 처리한다.
3. 스킬 이름이 로마자 줄임말이다(`gaejosik`, `pumui`, `gongmun`). 비개발자가 `/report-gaejosik`을 외우기 어렵다. 우리 명명(`doc-writer-word`처럼 영어 설명형)에 맞춰 바꿀지 결정이 필요하다(예: `report-bullet`, `approval-draft`). 이름은 사이트 노출과 호출 모두에 쓰이므로 사람이 정한다.
4. 빈 값은 `작성 필요`, `[확인 필요]`, `미정`, `메모에 없음(작성 필요)`이 섞여 있다. 우리 규칙은 `[확인 필요]`다. 통일이 필요하다(단 `미정`처럼 의미가 다른 것은 유지해도 된다).
5. 입력이 비었을 때 행동이 `meeting-to-todo`(6번 규칙)에만 있다. 나머지 스킬에는 "내용을 붙여 넣어 달라고 한 줄로 묻는다" 추가.
6. "내가 고칠 수 있는 설정"(말투·분량)이 없다. 개조식이라 말투는 고정이지만 분량·양식 선택 줄은 추가한다.
7. description이 길고(트리거 문구 나열) 자연어 호출용이다. 사이트 카드용 한 줄 설명은 별도로 만든다.

### 3-1. report-gaejosik (4점)
- 메모를 한국 회사식 개조식 보고서로 바꾼다. `□ ○ -` 3단계, `~함/~임`. 우리 `doc-writer-*`에 없는 형식이다.
- 인용: "원문에 결론이 없으면 `○ 원문에 결론 없음 [확인 필요]`라고 쓰고 지어내지 않습니다." "뺀 내용이 있으면 맨 끝에 한 줄로 알립니다."
- 더 나은 점: 개조식 기호와 끝맺음 규칙이 구체적이다. 원문 수치 외 계산 금지(5번 규칙)가 SPEC과 같은 방향이다. 예시 입출력이 현실적이다(복합기 교체 건).
- 부족한 점: 첫 질문이 없다(메모가 비었을 때). 보고 대상(팀장/임원)을 묻지 않는다. 개조식 문체를 낯설어할 수 있어 "~합니다체가 필요하면 말씀해 주세요" 같은 대안이 없다.
- 고칠 목록: 공통 1·3·4·5, 개조식이 아닌 문체 요청 시 처리 한 줄, 원문 길이가 길 때 분할 안내 한 줄.

### 3-2. weekly-report (4점)
- 한 주 메모를 주간보고로. 인용: "다음 주 계획이 메모에 없으면 `메모에 없음(작성 필요)`이라고 씁니다." "완료 여부가 메모에서 분명하지 않으면 `진행 중(확인 필요)`".
- 더 나은 점: 개인정보가 보이면 `[개인정보 삭제]`로 바꾸고 알린다(6번 규칙). SPEC의 "내부 정보·개인정보 확인"에 가까운 동작이다.
- 부족한 점: 개인정보를 확인 없이 삭제하는 쪽이라 우리 "넣기 전에 확인"과 약간 다르다. 용어 `[개인정보 삭제]`는 사용자가 의도하지 않았을 수 있어 "삭제했다고 알림"이 필요하다(이미 끝에 한 줄 알림 있음). 입력이 비었을 때 행동이 없다.
- 고칠 목록: 공통 1~5, 기간(이번 주 날짜)을 묻는 한 줄 추가.

### 3-3. meeting-to-todo (4점)
- 회의 메모를 할 일 표(할 일, 담당, 기한, 근거 문장)와 결정 3줄로. 인용: "근거를 댈 수 없는 할 일은 표에 넣지 않습니다." "메모가 비어 있거나 회의 내용이 아니면 표를 만들지 않고 무엇이 필요한지 한 줄로 묻습니다."
- 더 나은 점: 근거 문장 칸이 있어 환각을 검증하기 쉽다. 입력 부족 시 행동이 있는 유일한 스킬이다. 표 출력은 복사 붙여넣기에 좋다.
- 문제점(고쳐야 한다):
  1. 결정 사항이 "정확히 3줄"이다. 결정이 4개 이상이면 일부가 빠진다. "3줄"을 "결정된 것 전부(없으면 `추가 결정 없음`)"로 바꾸거나, 3개 넘으면 모두 쓰고 알린다.
  2. 고객 정보 가리기가 기본값이다(`[고객A]`). 사용자가 모르면 결과가 낯설다. 가렸다는 사실과 "원래 이름이 필요하면 말씀해 주세요"를 맨 위에 알려야 한다.
  3. 표에 기호 `|`가 있는 내용이 들어가면 깨질 수 있다. 마크다운 표 환경 의존이다. 화면에 표가 안 보이면 목록으로 바꾼다는 한 줄 필요.
- 고칠 목록: 위 3개 + 공통 1·3·4.

### 3-4. pumui-draft (4점)
- 메모를 품의서·기안문 초안으로. 인용: "단가와 수량이 둘 다 원문에 있을 때만 곱해서 합계를 쓰고 `(원문 단가 x 수량)`이라고 표시합니다." "「업무 효율 30% 향상」처럼 원문에 없는 수치나 효과를 만들지 않습니다."
- 더 나은 점: 예산·기대 효과 부풀리기 금지가 구체적이다. 우리 `doc-writer-word`의 "지어내지 않습니다"보다 상세하다. 붙임은 언급된 자료만.
- 부족한 점: 품의서 양식은 회사마다 다르다는 점을 이미 반영했다(양식 우선). 부가세 확인 문구가 좋다. 입력이 비었을 때 질문이 없다.
- 고칠 목록: 공통 1~5. "승인 권한·결재선은 추정하지 않는다"(`doc-hwp`의 `kr-official-forms.md`에 있는 문장)를 한 줄 가져오면 더 안전하다.

### 3-5. gongmun-tone (4점)
- 일반 글을 공문 어투로, 반대로 공문을 쉬운 말로. 인용: "원문에 없는 날짜, 기관명, 담당자, 연락처, 근거 법령, 문서번호를 만들지 않습니다." 반대 방향 출력 맨 위에 "그래서 내가 할 일".
- 더 나은 점: 양방향이라 받은 공문을 이해하는 데도 쓴다. 비개발자에게 유용하다. 날짜 표기 규칙(`2026. 10. 8.(목)`, `끝.`)이 구체적이다.
- 주의할 점:
  - 방향 판단이 모호할 수 있다. "분명하지 않으면 입력이 이미 공문 형식이면 풀어 쓰기, 아니면 공문으로 쓰기"로 기본값이 있다. 그래도 어느 쪽으로 했는지 한 줄 알림을 넣는 편이 안전하다.
  - 인사 문구 "귀 기관의 무궁한 발전을 기원합니다" 등 관용 표현이 현재 공문 관행에 맞는지는 확인하지 못했다. 공문 표기 규칙(항목 부호, 날짜, `끝.` 위치)도 `[확인 필요]`로 표시하고 제출처 양식을 우선한다는 문구를 추가한다.
  - 우리 `doc-writer-hangul`(공문 포함)과 범위가 일부 겹친다.
- 고칠 목록: 공통 1~5, 관용 문구·표기 규칙에 `[확인 필요]`와 "제출처 양식 우선" 한 줄, 어느 방향으로 처리했는지 알림.

### 3-6. email-reply-kr (5점)
- 곤란한 업무 메일 답장(거절·미룸·재촉·범위 밖·사과). 인용: "결론이 없으면 초안을 쓰지 말고 **한 번만** 묻습니다. 예: 「이번 요청은 거절할까요, 일정을 미룰까요, 일부만 받을까요?」" "사용자가 말하지 않은 약속을 쓰지 않습니다."
- 첫 질문, 기본값(상대 관계 없으면 고객으로 보고 가장 정중하게), 입력 부족 시 행동, 출력 틀, 넣지 않은 것 알림이 모두 있다. SPEC 요건 충족도가 후보 중 가장 높다.

- 고칠 목록: 공통 1·3·4. 그 외 수정 거의 없음.

### 3-7. pii-mask-before-ai (3점)

- 우려:
  1. 규칙 기반 가리기를 LLM이 하므로 놓칠 수 있다(스킬도 인정). 비개발자는 "가렸으니 안전"으로 받아들일 위험이 있다. 위 경고를 출력 맨 위에 항상 두는 규칙이 있지만, 설명 카드와 description에도 같은 한계를 적어야 한다.

  3. 우리 AGENTS.md의 "배포 스킬에 개인 정보를 넣지 않는다"와는 충돌하지 않는다(예시 번호는 가상값). 단 예시 파일의 값은 직접 확인하지 못했다(미확인).

- 새 분야(SNS 콘텐츠)다. 출력 틀이 명확하다.
- 부족한 점: 주제만 받고 지어내기 방지가 없다(통계·사례를 만들 수 있다). 입력 부족 시 행동 없음. 해시태그에 영어 혼합, 이모지 CTA. 표지 "15자 이내" 같은 수치 제약은 근거가 없다.
- 고칠 목록: 지어내지 않기·`[확인 필요]` 규칙 추가, 이모지·홍보·중복 프롬프트 삭제, 주제를 안 줬을 때 질문, 플랫폼(인스타/카카오) 기본값. 수요가 검증되지 않았으므로 후순위.

### 4-5. korean-report-summarizer (2점, 참고만)
- 보고서를 3줄 요약 + 액션 5개 + 소셜카드 한 줄.
- 문제: "액션 아이템 5개"라는 고정 개수가 문서에 없는 항목을 만들게 한다. "문서에 명시 안 된 액션도 맥락상 필요하면 `(제안)` 표시 후 포함"이라고 허용한다. 우리 원칙과 어긋난다. 예시도 "2초 이내로 최적화" 같은 원문에 없는 목표를 넣었다. "소셜카드 한 줄"은 한국 사무직 일반 용도와 맞지 않는다.
- 판정: 참고만. 요약 용도는 stanlee7 `report-gaejosik`이 더 낫다.

### 4-6. korean-one-page (1점, 참고만)
- A4 한 장 HTML 안내문. 본문이 `python "${CLAUDE_SKILL_DIR}/scripts/hanjang.py" render ...` 실행을 지시한다. 파이썬과 번들 스크립트(24.6KB)가 있어야 한다.
- 비개발자가 SKILL.md 하나만 받아서는 동작하지 않는다. JSON 초안, `--measure`, 종료 코드, `python`/`python3`/`py` 구분 등 개발자 전제가 많다. 우리 "평문 지시문만 담는다"와 맞지 않는다.
- 쓸 만한 아이디어: 기준일·출처 필수, 쉬운 말 점검, "한자어보다 쉬운 말(익일→다음 날)". 평문 안내문 스킬을 새로 만들 때 참고할 수 있다.
- 판정: 채택 불가.

### 4-7. korean-code-review (1점, 참고만)
- 개발자용 코드 리뷰. SkillBite 대상(비개발자)이 아니다. 채택하지 않는다.

## 6. 추천 우선순위 (적합성 기준)

## 7. 직접 못 본 것 (미확인)
- 위에서 '미확인'으로 적은 reference 파일과 예시 파일.
- 실제 Claude 화면에서 각 스킬을 돌려 본 결과. 이 검토는 원문 읽기만 했고 실행 품질(결과 문장의 자연스러움)은 확인하지 못했다. 채택 전에 같은 입력으로 시험 실행하는 단계가 필요하다.
