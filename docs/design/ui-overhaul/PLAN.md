# 프론트 개편 계획 (AI 티 나지 않는 운영 사이트 수준)

상태: 계획 확정, 아직 구현 전. 작성일: 2026-10-25.

## 목표

지금 화면은 "AI가 만든 템플릿" 같은 인상이 있다. 실제로 운영되는 서비스처럼 보이게 화면을 다시 만든다. 출발점은 목록(`/`)과 상세(`/skills/:id`)이고, 화면 수는 고정하지 않는다(아래 "화면 범위"). 기준은 `docs/brand-brief.md`(성격 친절한·단정한·믿음직한, 노랑 `#F5C842` + 회흑 `#242424`)와 현재 로고다. 로고는 확정이 아니라 언제든 변경 가능하다.

## 기준 문서는 고정이 아니다

`DESIGN.md`, `AGENTS.md`, `docs/PRD.md` 등 기존 문서가 항상 맞는 것은 아니다. 조사나 리뷰에서 근거가 나오면 **필요한 만큼 갱신한다.**

- `DESIGN.md`는 이번 개편의 결과로 다시 쓴다. 개편 전까지는 참고만 하고 따르지 않는다.
- `AGENTS.md`도 갱신할 수 있다. 단, 지침 변경은 같은 PR에 담고 PR 설명 맨 위에 "무엇을 왜 바꿨는지"를 적으며, 끝난 뒤 사용자에게 알린다.
- 특히 `AGENTS.md`의 "반드시 지킬 것"(정적 사이트, 데이터만 추가해도 늘어남, 확인 안 된 값은 `[확인 필요]`)을 바꾸는 일은 영향이 크므로 바꾸기 전에 사용자에게 먼저 묻는다. 그 전까지는 지킨다.
- 갱신한 내용과 이유는 `LOG.md`에 적는다.

## 화면 범위

목록과 상세는 출발점일 뿐이다. 조사 결과 운영 사이트에 필요하다고 판단되면 화면을 늘린다(예: 소개, 사용 방법, 자주 묻는 질문, 404). 늘릴 때는 다음을 지킨다.

- 조사 문서에 "왜 이 화면이 필요한가"를 근거와 함께 적는다.
- 가짜 정보로 채우지 않는다. 내용이 없으면 화면을 만들지 않는다.
- 화면을 추가·삭제하면 `docs/PRD.md`, `docs/HANDOFF.md`의 화면 목록도 같이 갱신한다.

## 도구 선택

한쪽만 고르지 않고 역할을 나눈다.

| 도구 | 맡길 일 | 이유 |
| --- | --- | --- |
| `frontend-design` 스킬 | 구현 | 템플릿 같은 기본값을 피하고 미학 방향·타이포를 의도적으로 고르게 하는 안내서다. 방금 설치한 `claude-code-plugins`의 것이다. omc에는 같은 이름의 스킬이 없고 `designer` 에이전트가 있다. |
| 조사용 서브 에이전트 | 레퍼런스 조사 | 실제 운영 사이트를 근거 있게 모은다. 구현자와 분리해 결과만 문서로 받는다. |
| Codex(`codex exec`) | 독립 리뷰 | 구현한 Claude와 다른 모델이 보게 해서 같은 편향을 피한다. |
| Claude 리뷰 에이전트(새 세션) | 2차 리뷰 | 구현 맥락을 모르는 상태에서 같은 기준표로 본다. |
| GSD UI 스킬(`gsd-ui-phase`, `gsd-ui-review`) | 보조 | `.planning/` 구조를 전제로 만든 도구다. 이 프로젝트에는 `.planning/`이 없고 단독으로 도는지 확인하지 못했다. 쓰기 전에 한 번 시험하고, 안 되면 아래 기준표를 직접 쓴다. |

선택 근거 한 줄: GSD는 프로젝트 전체 관리용이라 이 정적 사이트에는 무겁고, `frontend-design`은 구현 품질에는 좋지만 검증이 없다. 그래서 구현은 `frontend-design`, 검증은 다른 모델로 나눈다.

## 작업 절차 (화면마다 반복)

대상 순서(기본값): 1) 목록 `/` 2) 상세 `/skills/:id` 3) 공통(헤더·푸터·404·메타) 4) 조사에서 필요하다고 나온 추가 화면. 순서와 범위는 조사 결과에 따라 바꿀 수 있다.

1. **조사.** 서브 에이전트가 실제 운영 중인 사이트 5~8곳을 조사한다(예: Raycast Store, Notion 템플릿, Gumroad, Zapier 템플릿, 국내 서비스). 확인한 것만 쓰고 못 본 건 `미확인`으로 적는다. 결과는 `research/<화면>.md`에 저장한다. 레이아웃 패턴, 타이포 위계, 여백, 신뢰 요소, 흔한 AI 티 패턴을 정리한다.
2. **방향 확정.** 조사 결과로 방향 2~3개를 제안하고 사용자가 하나를 고른다. 이름·방향처럼 결과가 크게 달라지는 결정이라 이 단계만 확인을 받는다. 확정된 값은 `DESIGN.md`로 옮기고, 기존 문서와 어긋나면 해당 문서를 함께 갱신한다.
3. **구현.** `frontend-design` 스킬로 구현한다. 브랜치는 `feat/ui-<화면>`, `dev`로 PR한다.
4. **증거 수집.** 1440 · 768 · 390 · 320px 스크린샷을 `screenshots/round-N/`에 저장한다. 빌드 통과를 확인한다.
5. **독립 리뷰.** 아래 기준표로 Codex와 Claude 리뷰 에이전트가 따로 평가한다. 결과는 `reviews/round-N-codex.md`, `reviews/round-N-claude.md`에 그대로 저장한다.
6. **수정 반복.** 두 리뷰의 공통 지적부터 고친다. 최대 3라운드. 두 리뷰 모두 모든 항목이 3점 이상이면 끝낸다. 3라운드 후에도 남은 항목은 `LOG.md`의 "남은 것"에 적고 사용자에게 알린다.
7. **기록.** 라운드마다 `LOG.md`에 한 일, 점수, 고친 것, 남은 것을 적는다.

## 편향을 줄이는 규칙

- 구현한 에이전트는 리뷰하지 않는다.
- 리뷰어에게는 기준표, 스크린샷, 소스만 준다. 구현자의 설명과 의도는 주지 않는다.
- 점수와 근거 문장을 항목별로 받는다. "좋아 보임" 같은 총평만 받으면 다시 요청한다.
- 두 리뷰가 크게 갈리면(2점 이상 차이) 근거를 비교해 사용자에게 보여준다. 어느 쪽이 맞는지 임의로 정하지 않는다.
- 리뷰어가 칭찬만 하지 않도록 "AI가 만든 것처럼 보이는 곳 3개를 반드시 찾을 것"을 요구한다.

## 리뷰 기준표 (항목마다 1~5점)

1. **AI 티 없음.** 반짝이·그라데이션·글로우·유리 효과·이모지 장식이 없고, 같은 모양 카드를 아이콘·제목·설명으로 반복하는 템플릿 느낌이 없다.
2. **위계.** 제목, 부제, 본문, 행동 버튼의 크기와 굵기 차이가 분명하고 눈이 가는 순서가 자연스럽다.
3. **여백과 리듬.** 간격이 일정한 규칙을 따르고 빈 곳이 의도해 보인다. 스킬이 1개일 때도 어색하지 않다.
4. **브랜드 일치.** 현재 로고와 노랑·회흑, Pretendard가 화면 전체에서 일관된다. 임의의 파랑·보라가 없다. 단, 로고는 확정이 아니므로 로고 모양에 의존한 디자인은 감점한다.
5. **신뢰.** 가짜 평점·다운로드 수·후기가 없고, 확인되지 않은 값은 `[확인 필요]`로 표시되어 있다. 무료·가입 불필요 같은 사실이 명확하다.
6. **운영 사이트 완성도.** 푸터 정보, 404 페이지, 공유 미리보기(OG), 파비콘, 로딩 속도, 키보드 접근, 대비가 갖춰져 있다.
7. **반응형.** 1440 · 768 · 390 · 320px에서 가로 넘침과 잘림이 없다.
8. **비개발자 이해도.** 처음 온 직장인이 5초 안에 "무엇을 주는지, 어떻게 쓰는지"를 말할 수 있다.

## Codex 리뷰 실행 방법

```
codex exec -s read-only -C <프로젝트 폴더> \
  -i screenshots/round-N/home-1440.png -i screenshots/round-N/home-390.png \
  "docs/design/ui-overhaul/PLAN.md의 '리뷰 기준표'로 항목별 점수와 근거를 쓰고, AI가 만든 것처럼 보이는 곳을 3개 이상 찾아라. 파일은 수정하지 마라." \
  > docs/design/ui-overhaul/reviews/round-N-codex.md
```

- 읽기 전용(`-s read-only`)으로만 실행한다.
- 외부 서비스로 소스와 스크린샷이 전송된다. 이 프로젝트는 시크릿이 없는 정적 사이트이지만, 보내기 전에 `.env*`, 키 파일, 개인 정보가 없는지 확인한다. 사용자가 Codex 리뷰를 요청했으므로 이 용도로는 별도 확인을 하지 않는다.
- `--dangerously-bypass-approvals-and-sandbox`는 쓰지 않는다.

```
├─ reviews/           라운드별 Codex·Claude 리뷰 원문

```

## 열린 항목

- GSD UI 스킬이 `.planning/` 없이 단독으로 도는지 (시험 전까지 미확인).
- 상세 화면의 "결과물" 영역에 쓸 실제 자료(스크린샷·예시). 없으면 구성 예시로 표시한다.
- 윈도우 설치 경로, 피드백 URL은 계속 `[확인 필요]`.
- 로고는 확정이 아니다. 디자인 값(색·글꼴·형태)을 로고에 맞춰 굳히지 말고, 로고가 바뀌어도 쉽게 따라가도록 색은 CSS 변수로, 로고는 `public/logo.svg`·`public/favicon.svg` 한 곳에서만 쓴다. 바뀌면 `docs/design/logo-candidates/`와 `public/`의 아이콘 파일(`favicon.ico`, PNG, `apple-touch-icon.png`)을 함께 갱신한다.
